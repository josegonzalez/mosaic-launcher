# core-prefetch

Warms a game's core before it launches, so it starts faster. In `pre_launch` it finds the emulator pak the game launches with, the way stock does, or the one `emulator-override` chose for it when `emulator-override=on` is in `plugins.txt` and the choice is a pak on the card. It reads that pak's `launch.sh` for its core, which works for scripts that set `EMU_EXE` and run `"$CORES_PATH/${EMU_EXE}_libretro.so"`, as stock's paks all do, with the core in `.system/<platform>/cores/` or, with `CORES_PATH=$(dirname "$0")`, in the pak itself; for any other script it says in the launcher log that it can't tell which core runs. Then it asks the kernel to read the core, and then the game (the first disc of a `.m3u`, and the first file a `.cue` names, with the `rom` setting, on by default), into the page cache with `posix_fadvise(POSIX_FADV_WILLNEED)`, a 1 MB chunk at a time. The reading goes on while the launcher exits and the pak's script starts. It only opens files read-only: it never writes anything, starts a process or cancels a launch, and opens only regular files on the card, with links resolved. It stops at the `max_mb` setting (16 by default) across the files, and starts no chunk once the `max_ms` setting (20 by default) has passed since `pre_launch` began, so that's about how long it can add to a launch. Paks aren't warmed. With another plugin that replaces launches earlier in load order than `emulator-override`, it can warm a different core than the one that runs. On desktop, or without `posix_fadvise`, as on macOS, it loads but logs that it's unsupported and does nothing, and its name on the Plugins page says so. From MinUI-Zero.
